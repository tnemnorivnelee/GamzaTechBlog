## 찝찝함의 시작
![Uploaded Image](https://gamzatech-bucket.s3.ap-northeast-2.amazonaws.com/post-images/110/b16ee56b-66a6-4f48-8123-f50ea444b706_image.png)

2학기, 졸업 프로젝트가 시작되었다.

이전 "감자 기술 블로그" 프로젝트에서 Next.js의 SEO와 SSR에 매료되었던 나는 망설임 없이 새 프로젝트도 Next.js로 선택했다.

그런데 퍼블리싱이 거의 끝나가는 시점, 뭔가 찝찝한 느낌이 들기 시작했다.

>**'이 프로젝트에 정말 Next.js가 필요했을까?'**

기술 선택에 정답은 없다지만, 프로젝트를 다시 살펴보니 Next.js의 핵심 기능들을 제대로 활용하지 못할 것 같았다. 

그래서 Next.js와 Vite+React에 대해 다시 깊이 파헤쳐보기로 했다.


## 프로젝트 소개: FlowPlan

이번 프로젝트 **FlowPlan**은 'AI 기반 WBS 자동 생성 웹 서비스'다.

프로젝트를 진행하면서 항상 느꼈던 기획의 어려움, 특히 WBS(Work Breakdown Structure) 작성의 어려움을 해결하고자 시작했다. 

기획의 중요성은 알지만 어디서부터 어떻게 시작해야 할지 막막했던 경험에서 출발한 프로젝트다.

**주요 기능은 이렇다:**
- WBS 테이블 작성 및 편집
- 간트차트 시각화
- 칸반보드 기반 작업 관리

그리고 여기서 문제가 시작되었다.

> **이 모든 기능이 사용자 인터랙션 중심이라는 것.**

직전 프로젝트인 "감자 기술 블로그"에서 Next.js의 SEO, SSR, ISR 같은 기능에 큰 매력을 느꼈고, 이런 기능들을 이번 프로젝트에서도 활용하기 적합하다고 판단했다.

하지만 퍼블리싱이 막바지에 이르자 깨달았다. 

**생각보다 서버 컴포넌트로 설계할 부분이 거의 없다는 것을.**

WBS 테이블, 간트차트, 칸반보드가 메인 기능인 프로젝트에서 서버 컴포넌트로 구현할 부분이 거의 없어 보였다.


## Next.js vs Vite+React: 무엇이 다른가

아래는 Next.js와 Vite+React의 차이점을 정리한 표다.

| 구분 | Next.js가 필요한 서비스 | Vite + React가 더 나을 수 있는 서비스 |
|---|---|---|
| **핵심 가치** | 콘텐츠, 검색 노출, 첫인상 | 기능, 상호작용, 데이터 처리 |
| **렌더링** | 서버 사이드 렌더링 (SSR/SSG) | 클라이언트 사이드 렌더링 (CSR) |
| **주요 예시** | 블로그, 뉴스 사이트, 이커머스 쇼핑몰 | 관리자 페이지, 분석 대시보드, 웹 기반 편집 툴 |
| **SEO 중요도** | 매우 높음 (사업과 직결) | 매우 낮음 (로그인 장벽 뒤) |
| **초기 로딩 속도** | 매우 중요 | 상대적으로 덜 중요 |
| **아키텍처** | 프레임워크 (정해진 규칙 존재) | 라이브러리 조합 (높은 자유도) |

표를 보면 명확하다. 내 프로젝트는 오른쪽 열에 정확히 들어맞는다:

그런데 나는 Next.js를 선택했다. 왜? 
**이전 블로그 프로젝트의 성공 경험에만 의존했기 때문이다.**

### Next.js의 특징

Next.js는 **프레임워크**다. 정해진 규칙이 존재한다.

편리하지만 이면의 **무거움**과 **정해진 규칙**이 때로는 단점이 되기도 한다. 
특히 순수한 클라이언트 인터랙션 중심 앱을 만들 때는 오버킬이 될 수 있다.

### Vite+React의 특징

Vite+React는 **라이브러리 조합**이다.

**가볍고, 빠르며, 개발의 자유도**가 매우 높다. 

지금 Next.js로 개발하면서 느끼는 것은 'use client'를 어디에 붙여야 할지, 어떤 부분을 서버 컴포넌트로 만들어야 할지 끊임없이 고민해야 한다는 점이다.

만약 Vite+React로 시작했다면? 모든 컴포넌트가 클라이언트 컴포넌트이므로 이런 고민 없이 기능 개발에만 집중할 수 있었을 것이다.

### UX 관점에서의 차이

나는 프론트엔드에서 가장 중요한 것을 하나만 꼽자면 단연 **UX**라고 생각한다.

프론트엔드는 사용자가 직접 마주하는 부분을 개발하기 때문에, 사용자가 해당 서비스에 매력을 느끼고 불편함을 느끼지 않도록 하는 것이 가장 중요하다.

**Next.js의 강점: 첫 인상**
- 초기 로딩 속도가 빠르다
- 서버에서 미리 완성된 HTML을 보내주기 때문에 사용자는 로딩없이 콘텐츠를 즉시 볼 수 있다

**Vite+React의 강점: 앱 내부 경험**
- CSR 기반으로 앱이 한번 로드되면, 이후의 모든 작업은 페이지 전체를 새로고침하지 않고 브라우저 내에서 즉각적으로 일어난다
- 매우 빠르고 부드러운 UX를 제공한다

이런 관점에서 보았을 때, 이번 프로젝트는 **앱 내부 경험**이 훨씬 중요한 서비스였다. Next.js보다는 Vite+React로 진행하는 것이 더 나은 선택이었을지도 모른다는 생각이 든다.

## 간단한 판단 기준: R vs CUD

프레임워크 선택이 고민된다면, CRUD로 생각해보자.

### R (Read) 중심이라면 → Next.js

**특징:**
- 블로그, 뉴스 사이트, 포트폴리오, 이커머스 상품 페이지
- 검색 노출이 중요
- 사용자가 페이지에 접속했을 때 빠르게 콘텐츠를 보여주는 것이 핵심
- 서버에 이미 존재하는 콘텐츠를 효율적으로 전달하는 것이 목표


**Next.js가 강한 이유:**
- SSR/SSG로 미리 데이터를 읽어서 완성된 HTML을 제공
- 검색 엔진 봇이 콘텐츠를 쉽게 읽을 수 있음
- 캐싱으로 반복 방문 시 더 빠른 로딩 가능

### CUD (Create, Update, Delete) 중심이라면 → Vite + React

**특징:**
- 대시보드, 관리자 페이지, 웹 에디터, 프로젝트 관리 툴
- 로그인 후 사용
- 빠르고 부드러운 인터랙션이 핵심
- 사용자의 잦은 상호작용으로 화면이 계속 변하는 것이 중요

**Vite+React가 강한 이유:**
- 앱이 한번 로드되면 페이지 새로고침 없이 모든 작업이 클라이언트에서 즉각 처리
- 풍부한 인터랙션에 최적화
- 필요한 데이터만 서버와 주고받으며 동적으로 화면 업데이트

### 내 FlowPlan은?

명백히 **CUD 중심**이었다.

1. 사용자가 WBS 테이블을 만들고 (Create)
2. 간트차트에서 일정을 수정하고 (Update)
3. 칸반보드에서 카드를 이동하고 (Update)
4. 불필요한 작업을 삭제한다 (Delete)

이전 프로젝트인 기술 블로그는 **R 중심**이었기에 Next.js가 완벽한 선택이었다. 하지만 이번엔 달랐다.

---

## 그래서 어떻게 할 것인가?

이미 Next.js로 퍼블리싱이 거의 끝난 상황. 
지금 와서 Vite로 갈아타는 건 현실적으로 불가능하다.

하지만 이번 경험에서 배운 것들이 있다.

### 1. 다음 프로젝트를 위한 교훈

**기술 선택 전 체크리스트:**
- [ ] 이 프로젝트는 R 중심인가, CUD 중심인가?
- [ ] SEO가 정말 필요한가?
- [ ] 초기 로딩 vs 앱 내 인터랙션, 무엇이 더 중요한가?
- [ ] 이전 프로젝트의 경험에만 의존하고 있지 않은가?

**이번에 느낀 점:**
- 프로젝트 성격에 따라 알맞는 도구를 선택해야 한다

### 2. 그래도 Next.js로 계속 진행한다

Next.js도 분명 강력한 프레임워크다. 

서버 컴포넌트와 클라이언트 컴포넌트를 적절히 활용하면 "빠른 초기 로딩"과 "부드러운 인터랙션" 둘 다 잡을 수 있다고 생각한다.


완벽한 선택은 아니었지만, 완성도 있는 결과물을 만드는 데 집중하려 한다.
### 2. 다음 프로젝트를 위한 교훈

**1. 기술 선택은 유행이 아니라 프로젝트 특성으로**
- 내 프로젝트의 핵심 가치가 무엇인지 먼저 파악하기

**2. 'R 중심인가, CUD 중심인가' 먼저 질문하기**
- 이 간단한 질문 하나로 프레임워크 선택이 명확해진다
- 두 가지가 섞여있다면? Next.js의 하이브리드 구조 활용

**3. 이전 경험의 성공에만 의존하지 않기**
- 블로그에서 Next.js가 좋았다고 해서 모든 프로젝트에 좋은 것은 아니다
- 각 프로젝트의 특성을 새롭게 분석하는 습관

### 3. 그래도 배운 건 많다

이 과정에서 얻은 것들:
- Next.js App Router와 서버 컴포넌트 개념을 깊이 학습
- SSR과 CSR의 차이를 몸소 체험
- 프레임워크 선택의 트레이드오프를 이해
- 기술 선택에 대한 사고 체계 확립

## 마치며

**더 나은 선택을 하고 싶었지만, 최선의 결과를 만들어낼 것이다.**

프로젝트는 이미 시작되었고, 되돌리기엔 늦었다..

하지만 Next.js 내에서도 클라이언트 중심 경험을 최적화할 수 있는 방법들이 있다. 
그 방법들을 최대한 활용해서 좋은 결과물을 만들어낼 계획이다.

혹시 지금 프레임워크 선택으로 고민 중이라면, 이 글이 작은 도움이 되길 바란다.

**당신의 프로젝트는 R 중심인가요, CUD 중심인가요?**

이 질문 하나로 선택이 훨씬 명확해질 것이다.
