# REST API 란?

REST 원칙을 적용하여 설계한 서비스 API를 말한다.

---

## 용어 정리

### REST

- 자원을 이름으로 구분하여 해당 자원의 상태를 주고받는 모든 것을 의미한다.
- HTTP URI를 통해 자원을 명시하고, HTTP method를 통해 해당 자원에 대한 CRUD를 적용한다.
- 자원 기반의 구조 설계의 중심에 자원이 있고, HTTP method로 처리한다.

### API

- 응용프로그램에서 사용할 수 있도록 운영체제나 프로그래밍 언어가 제공하는 기능을 제어할 수 있게 만든 인터페이스이다.
- 쉽게 말해 식당에서의 메뉴판과 비슷하다. 손님(클라이언트)이 메뉴판(API)을 보고 주문하면 주방(서버)이 요리를 만들어 내보내는 것처럼, 프로그램끼리 통신할 수 있도록 하는 중재자 역할이다.

### URI (Uniform Resource Identifier)

- 리소스에 접근할 수 있는 유일한 식별자를 의미한다.
- URI를 수신하는 기기는 해당 URI에 맞게 데이터를 반환한다.

---

## RESTful API

- 웹의 장점을 최대한 활용하기 위해 URI를 통해 자원을 명시하고, HTTP method를 통해 해당 자원에 대한 행위를 분리하여 설계하는 방식이다.
- 핵심은 "주소는 명사, 행위는 메서드"로 분리하는 것이다.

### RESTful 하지 않은 설계

```
GET /getUser/1
POST /deleteUser/1
POST /updateUserName/1
```

- 주소에 동사가 섞여 있어서 일관성이 없고, 메서드만 보고는 어떤 동작인지 알 수 없다.

### RESTful 한 설계

```
GET    /users/1       → 1번 유저 조회
DELETE /users/1       → 1번 유저 삭제
PATCH  /users/1       → 1번 유저 정보 일부 수정
```

- 누가 봐도 주소와 메서드만으로 어떤 목적의 요청인지 직관적으로 이해할 수 있다.

---

## HTTP Method

### GET

- 요청받은 URI의 정보를 검색하여 응답한다.
- 예: 유저 목록 페이지에 접속하면 브라우저가 `GET /users`를 보내서 유저 데이터를 받아온다.

### POST

- 요청된 자원을 생성한다.
- 예: 회원가입 폼에서 제출 버튼을 누르면 `POST /users`로 새로운 유저 데이터가 서버로 전송된다.

### DELETE

- 요청된 자원을 삭제한다.
- 예: 회원 탈퇴 버튼을 누르면 `DELETE /users/1`로 해당 유저가 삭제된다.

### PUT

- 요청된 자원 전체를 수정한다.
- 예: 프로필 전체를 새로 덮어쓰는 경우 `PUT /users/1`로 유저 정보를 통째로 교체한다.

### PATCH

- 요청된 자원 일부를 수정한다.
- 예: 닉네임만 변경하는 경우 `PATCH /users/1`로 닉네임 필드만 수정한다.
- PUT과의 차이는 전체 교체냐 부분 수정이냐의 차이이다.

### OPTIONS

- 웹 서버에서 지원되는 메서드의 종류를 확인할 경우 사용한다.
- 프론트 실무에서는 주로 크로스 도메인 요청 시 CORS 정책 위반 여부를 미리 확인하기 위한 Preflight로, 브라우저가 자동으로 보낼 때 마주하게 된다.
- 개발 중 네트워크 탭에서 본 요청의 OPTIONS가 바로 이것이다.

## CORS 에러

프론트엔드 개발을 하다 보면 로컬에서 API를 호출할 때 콘솔에 빨간 글씨로 CORS 에러를 한 번쯤은 마주하게 된다. 이 에러를 이해하려면 SOP와 CORS의 관계를 먼저 알아야 한다.

### SOP (Same-Origin Policy)

- 브라우저가 기본적으로 적용하는 보안 정책으로, 동일한 출처(프로토콜 + 도메인 + 포트)가 아닌 요청을 차단한다.
- 예를 들어 `http://localhost:3000`에서 `http://localhost:8080`으로 API를 호출하면 포트가 다르기 때문에 SOP에 의해 차단된다.
- 즉, 다른 출처의 리소스에 접근하는 것을 막는 정책이다.

### CORS (Cross-Origin Resource Sharing)

- SOP에 의해 차단된 다른 출처의 요청을 허용해 주는 정책이다.
- 흔히 "CORS 에러"라고 부르지만, 실제로는 서버에서 CORS 허용 설정이 되어 있지 않아 SOP에 의해 막힌 것이다. CORS는 오히려 문제를 해결해 주는 쪽이다.
- CORS는 본질적으로 브라우저가 서버에 "이 출처에서 요청해도 괜찮아?"라고 허락을 구하는 과정이므로, 백엔드 서버의 응답 헤더(`Access-Control-Allow-Origin` 등)에 프론트엔드의 도메인을 명시적으로 허용해 주도록 요청하여 근본적으로 문제 해결이 가능하다.

---

## 최종 정리

> REST API란 URI로 자원을 명시하고 HTTP method로 행위를 분리하여 설계하는 방식입니다. 핵심은 "주소는 명사, 행위는 메서드"로 분리하는 것으로, `/deleteUser`처럼 동사를 URI에 넣는 것이 아니라 `DELETE /users/1`처럼 주소와 메서드만으로 목적을 직관적으로 파악할 수 있게 만듭니다. 주요 HTTP method로는 조회의 `GET`, 생성의 `POST`, 삭제의 `DELETE`, 전체 수정의 `PUT`, 일부 수정의 `PATCH`가 있습니다. 프론트엔드 개발 시 자주 마주치는 CORS 에러는 사실 브라우저의 SOP(동일 출처 정책)에 의해 다른 출처의 요청이 차단된 것이고, CORS는 오히려 그 제한을 풀어주는 정책입니다. 따라서 백엔드 서버의 응답 헤더에 프론트엔드 도메인을 허용해 주는 것으로 해결할 수 있습니다.
